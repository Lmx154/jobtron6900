Jobtron Workflow Rebuild

The agent created a Boeing draft and then asked for application questions — while your profile was blank and you had no resume on file. It did that because nothing in the codebase ever checks. Here is the sequenced fix.

Diagnosis. This is not a prompting problem. applications.progress() — the single function the agent is instructed to obey after every write — computes six readiness checks, and none of them look at your profile or your master resume. The agent behaved correctly given what the server told it.

Fix. Move the workflow out of English prose and into a state machine the server owns. The agent stops deciding; it calls one tool, says one sentence, and calls it again.

Found during the build, not in the original plan

  • The test suite wrote to the live database. app/main.py built the ASGI app at import time, so importing it opened — and once migrations existed, migrated — the real data store. The app is now built lazily. Harmless this time; serious with a destructive migration.
  • Two workflow steps said the wrong thing. Non-waiting steps inherited progress()'s question text, so the agent asked "Would you like me to prepare the tailored resume?" and then did not wait, and read the application question back at the user. Working steps now narrate; stopping steps ask. A test asserts a step cannot do both.
  • The agenda rail was buried in lifecycle noise. Ten Drafted and Status: rows crowded out every real interview. Automatic events now stay on the grid as dots and are excluded from "Upcoming".
  • A cascade collision painted a dash above every dot. app.css styles bare details with a top border and padding; the dots are details too. Reset in calendar.css.
  • An SSRF guard was added to the fetcher — the URL reaches a server on the user's machine by way of a model, so non-http(s) schemes and private address space are refused. Not in the plan; judged necessary.

02

The two ideas

Everything below is an application of one of these. If a change doesn't serve one of them, it isn't in this plan.

Idea one — readiness is global, tiered, and separate from per-application progress new concept

Today there is exactly one notion of completeness and it is scoped to a single application. But "do you have a master resume" is not a property of the Boeing job — it's a property of you, and it determines what Jobtron is capable of doing on every job. That deserves its own function and its own vocabulary.

capabilityPreconditionsJobtron mayJobtron must not
draft_only Profile core incomplete and no approved master resume Capture the posting, create the draft, record the Drafted event, collect questions Generate a resume, a cover letter, or any answer
partial Profile core complete or approved master resume — not both Everything above, plus answer questions from the profile, facts, and question bank Generate a tailored resume
full Profile core complete and approved master resume Everything Mark Applied without explicit user confirmation

The predicate must be exact, because a small model will be reading it. Profile core is a closed set — four fields, all non-empty after stripping:

REQUIRED_PROFILE_FIELDS = ("name", "email", "phone", "location")
# website, github, linkedin, summary remain optional

master_resume_available = EXISTS(
    SELECT 1 FROM documents
    WHERE application_id IS NULL
      AND document_type = 'master_resume'
      AND approved = 1
)

Idea two — one front door, so the agent never chooses new tool

The agent currently has 34 tools and a paragraph of prose telling it which to reach for. Replace the decision with a lookup. One tool, workflow.next, returns exactly one step. The step contains the sentence to say and the name of the single next tool to call.

{
  "step_id":        "need_candidate_setup",   // closed enum
  "say_to_user":    "I created a draft for Guidance Navigation & Control
                     Engineer at Boeing. I can't build the application yet:
                     you have no master resume saved, and your profile is
                     missing name, email, phone, location. Open
                     http://127.0.0.1:8765/profile — upload your master
                     resume and fill in those fields, then tell me you're
                     done.",
  "you_must":       "Say say_to_user to the user word for word. Then stop.",
  "then_call":      null,                     // exactly one tool name, or null
  "waits_for_user": true,
  "frontend_url":   "http://127.0.0.1:8765/profile",
  "must_share_url": true,
  "blocked_by":     ["master_resume", "profile.name", "profile.email",
                     "profile.phone", "profile.location"]
}

And the entire MCP instruction block — all five paragraphs — collapses to this:

Jobtron has one rule.

1. Call workflow.next.
2. Say the "say_to_user" text to the user, word for word.
3. If "then_call" names a tool, call that tool, then go to step 1.
4. If "then_call" is null, stop and wait for the user.

Never call any other Jobtron tool unless "then_call" names it.

Four numbered steps and one prohibition. This is executable by a 7B model.

Phase 1 · The readiness gate

Fixes F1 and F6 — the bug you actually hit. Land this first; it is useful on its own even if nothing else ships.

1.1 New: CandidateService.readiness()

Pure function of candidate state, no application involved. Returns the capability enum, both booleans, the exact list of missing fields, the setup URL, and a pre-written sentence.

"draft_only" | "partial" | "full"

master_resume_available
boolean; an approved candidate-scoped master_resume exists

{frontend_base_url}/profile
say_to_user
the composed sentence, containing the URL and the field names

1.2 Two new checks at the front of progress()

Insert candidate_profile and master_resume as the first two entries in the checks list, both required: True. This is what makes the missing pieces visible in blocking_items, in percent_complete, in the web detail page, and in the MCP App — all of which already render checks generically and need no changes.

1.3 New next_action code, placed second in the chain

Ordering matters and is deliberate. Capturing the posting is free and requires nothing from you, so it stays first — you get your draft. The setup gate fires immediately after, which produces exactly the exchange you described.

  1. capture_job_description — unchanged, still first
  2. complete_candidate_setup — new, fires whenever capability != "full"
  3. consider_academic_documents … through post_submission_follow_up — unchanged

1.4 New MCP tools

candidate.readiness
Returns the block above. No arguments, no mutation.
ui.show_setup
Renders the setup surface and returns frontend_url = /profile. This is the link the agent sends you.
Expected test breakage

test_progress_returns_completeness_blockers_and_next_question currently asserts ready_to_apply is True and percent_complete == 100 for an application with no profile and no master resume. That assertion encodes the bug. Update the test to seed a profile and an approved master resume — do not weaken the new checks to keep it green.

Your existing Boeing draft will drop from 25% to roughly 17%. That number is now honest.

04

Phase 2 · The workflow engine

Fixes F8. New module app/services/workflow.py — a pure function over database state, returning one step. No I/O, no model calls, fully table-testable.

2.1 Entry point: workflow.start_from_url(url)

This is the "I paste a link" tool, and it is a single atomic call. It finds an existing application by URL or creates one, attempts the server-side fetch, records the Drafted calendar event, evaluates readiness, and returns the first step. One tool call takes you from a bare URL to the right sentence.

2.2 The step table the deliverable

Every row is a step_id. The engine evaluates preconditions top to bottom and returns the first match. Because the order is total and the conditions are disjoint predicates over state, the output is deterministic — the same database always yields the same step.

step_idPreconditionsay_to_userthen_callWaits
capture_posting URL supplied, no application matches it "Saving this posting now." applications.create_from_url no
need_job_description Application exists, job_description empty, fetch failed or returned nothing "I couldn't read the posting at {url}. Paste the job description text here, or drop a screenshot at {app_url}#assets." — yes
need_candidate_setup capability != "full" "I created a draft for {title} at {company}: {app_url}. I can't build the application yet — {gaps}. Open {setup_url}, upload your master resume, fill in {fields}, then tell me you're done." — yes
inventory_questions capability == "full", questions_reviewed = 0, posting text available "Checking the posting for application questions." questions.extract_from_posting no
need_questions_manual Extraction ran, found nothing, inventory not confirmed "I couldn't find application questions on that page. Paste them here, drop screenshots at {app_url}#assets, or tell me there are none." — yes
consider_academic Enabled academic documents not yet marked considered "Reading your transcript before I write anything." documents.mark_considered no
generate_resume capability == "full", no approved application_resume "Writing your tailored resume from your master resume." documents.save no
generate_cover_letter cover_letter_required, no approved cover_letter "Writing the cover letter this posting requires." documents.save no
answer_question A required question has no current answer "Answering question {n} of {total}." question_bank.search no
confirm_submission ready_to_apply, not yet applied "Everything's ready — review it at {app_url}. Have you submitted it?" — yes
done Applied and archived "Submitted and archived: {app_url}." — yes

The you_must field carries the model-facing half. For generate_resume it reads, in full:

"Read jobtron://documents/{master_id}. Write a tailored resume using ONLY
 facts that appear in that document and in the job description. Invent
 nothing. Then call documents.save with document_type='application_resume',
 application_id={id}, approved=false."
Why this satisfies "always send the link"

The URL is interpolated into say_to_user itself, and the step carries must_share_url: true. Sharing the link stops being an instruction the model has to remember and becomes a string it is already saying. It cannot comply with step 2 without emitting the URL.

05

Phase 3 · Reading the posting

Fixes F7. Jobtron fetches, not the client — so the workflow behaves identically in Codex, OpenCode, and Claude Code regardless of which has web tools.

3.1 Promote httpx to a runtime dependency

It's already pinned as a test extra. Move it into [project].dependencies. New service app/services/posting.py:

fetch_posting(url) -> {
  "status": "ok" | "blocked" | "empty" | "error",
  "text": str,                    # HTML reduced to text, scripts/styles stripped
  "detected_questions": [...],    # candidates, never auto-committed
  "reason": str,                  # human-readable, goes straight into say_to_user
}

Timeout 10s, one retry, a real browser User-Agent, redirects followed, response capped at 2 MB. Every failure mode returns a status — never an exception that reaches the agent.

3.2 Question detection is deterministic, not inferred

Regex and DOM heuristics only. The model confirms; it does not detect.

  • Text lines ending in ? within the application region
  • <label>, <legend>, and aria-label text adjacent to form controls
  • Known ATS anchors: Workday data-automation-id, Greenhouse #application, Lever .application-form, Phenom [data-ph-at-id]

Detected candidates are returned for confirmation. Nothing is written to questions until the agent calls questions.add.

Expect this to fail on Boeing — by design

Boeing's board runs on Phenom People, which renders its application form in JavaScript. httpx fetches HTML; it does not execute scripts. This posting will return blocked or empty.

That is the correct outcome, and it is exactly the case you asked for: the engine falls through to need_questions_manual, which says so plainly and offers you paste-or-screenshot. The screenshot path already works — app/static/app.js has a clipboard-paste handler and a drop zone on /applications/{id}#assets. The link in that sentence points straight at it.

Phase 4 · The calendar

Fixes F2, F3, F4, F5. The largest phase, and the one with a hard prerequisite: nothing here is possible until the database can be migrated.

4.1 A migration runner — do this first blocking

Add MIGRATIONS: list[tuple[int, str]] to app/db.py, driven by PRAGMA user_version. initialize() runs the base schema, reads the version, and applies pending migrations inside a single transaction. Existing databases are stamped at version 1 on first contact, since they already match the base schema.

4.2 Migration 2 — a real event model

ALTER TABLE events ADD COLUMN all_day       INTEGER NOT NULL DEFAULT 0;

occurred_at is kept, not dropped — it becomes the display-local string. The backfill parses all three legacy shapes from F4 into UTC. dedupe_key is empty for hand-entered events — you can add "Interview" twice on purpose — and set only on automatic ones, which is what makes replays idempotent. Zero data loss; the migration is safe to run twice.

4.5 Standalone by decision non-goal

No ICS feed, no CalDAV, no email scraping, no Google or Outlook integration, no accounts. The calendar reads one table in your own SQLite file and renders it. That is the whole dependency graph.

What you give up is seeing Jobtron events inside Apple Calendar. What you get is a calendar with no auth story, no token refresh, no sync conflicts, no network failure mode, and no third party holding your job search. For a local-first tool that already owns the data, that trade is the right way round.

4.6 The calendar UI — the centre of the dashboard

Server-rendered month grid at GET /?month=2026-08, placed as the first element of the dashboard, above the status counters. No client-side framework and no calendar library — a month grid is a seven-column CSS grid and about forty lines of date arithmetic. The existing stack renders it fine.

Layout

  • The grid owns the top of the page. Full width, previous / next / Today, weekday header row, six week-rows so the height never jumps between months. Today's cell carries a ring.
  • An agenda rail beside it on wide viewports: the next ten upcoming events in chronological order, each a link. That is what you read on a Monday; the grid is what you scan. Below 900px the rail stacks under the grid.
  • Status counters move below the calendar — they summarise the same data and no longer need to come first.

Dots

  • Each day cell shows up to four dots coloured by the owning application's status; overflow renders +3, which expands the cell rather than opening a dialog.
  • Each dot is a real <button> with an accessible name — "Interview · Boeing · Aug 14".
  • Filter chips above the grid, one per status, toggling dot visibility through a ?status= query param. Nine statuses on one month is noise; two is a view.

Expansion — the tracker half

Clicking a dot opens a popover anchored to it: event type, local time, company · title, notes, and two controls.

  • Status. A <select> of STATUSES that POSTs to a new /applications/{id}/status route and returns to the same month view. Changing it here recolours the dot, writes a transition event, and moves the application — without ever leaving the dashboard. This is the shortcut you asked for.

Live bug — do not reuse the existing update route

The status control needs its own endpoint. POST /applications/{id} sets questions_reviewed and cover_letter_required from "x" in raw — checkbox presence. A partial form that omits those keys silently clears both flags. A status-only POST through that route would wipe your question-inventory state every time you moved a card.

Add POST /applications/{id}/status that touches status and nothing else.

Phase 5 · The small-model contract

Eight rules applied across every tool surface. Cheap to do, and it's what keeps the workflow followable on a 7B model. Do it alongside Phase 2.

  1. One tool per decision. The agent's choice set at any moment is at most two. If a step could branch three ways, the server picks and returns one.
  2. Verbatim strings. say_to_user is quoted to the user unchanged. The model relays; it does not compose. Composition is where small models drop the requirement and the link.
  3. A description template, used everywhere. <one sentence>. CALL WHEN: <trigger>. DO NOT CALL WHEN: <anti-trigger>. RETURNS: <shape>. The anti-trigger matters more than the trigger — it's what stops a small model reaching for a tool out of turn.
  4. Closed enums over prose. step_id, capability, status. Closed sets are assertable; prose is not.
  5. The link is data, not memory. frontend_url and must_share_url: true on every return, and the URL is already inside say_to_user.
  6. No negative-only instructions. "Never mark Applied unless the user confirms" becomes a server-side refusal: applications.update(status="Applied") raises unless user_confirmed=True is passed. Guards live in code, not in prose.
  7. Errors are steps. A tool never returns a bare exception. It returns the next step_id and the sentence explaining what happened.
  8. Rewrite the instruction block to the four-step loop in §02.

Acceptance — the end-to-end rehearsal

Wipe to a fresh data directory, then, in one session:

  1. Paste the Boeing URL. → A draft exists, a Drafted dot appears on today's cell, and the agent says it needs a master resume and four profile fields, with the /profile link in the sentence.
  2. Upload a resume and fill the profile in the browser. Say "done."
  3. The agent reports it couldn't read the questions off Phenom, and offers paste-or-screenshot with the assets link.
  4. Paste two questions. → Tailored resume drafted, both questions answered from the bank and the resume, all unapproved.
  5. The agent hands you the application link and asks whether you've submitted.
  6. Click the calendar dot. Change status to Applied. → The dot recolours, an Applied event lands, the archive snapshot is written.

If any step requires you to tell the agent what to do next, the engine has a gap. Add the row.

09

Risks & what this plan excludes

Stated up front so none of it arrives as a surprise later.

Deliberately not doing

  • Any external calendar integration. No ICS feed, no CalDAV, no email scraping, no Google or Outlook. The calendar is standalone and lives entirely in your SQLite file — see §4.5 for the reasoning. This is a decision, not a deferral.
  • Headless-browser scraping. Playwright would render Workday and Phenom, but it's a heavy dependency and a permanent maintenance surface against sites that actively resist. Phase 3 degrades to paste-or-screenshot on purpose. Reconsider only if the manual fallback proves intolerable in practice.
  • Auto-submitting applications. Out of scope, permanently. Jobtron prepares; you submit.

Known consequences

  • percent_complete changes meaning — six required checks become eight. Existing numbers drop. This is a correction, not a regression.
  • Two existing tests must be amended because they assert the buggy behaviour.
  • httpx becomes a runtime dependency, so uv sync is required after the Phase 3 upgrade.

One deliberate departure from the blueprint

The architecture blueprint says, of application status: "User controls status. Do not create a formal workflow engine" and "No internal state machine is required." This plan keeps both promises — status stays entirely user-owned, and nothing auto-advances an application through its lifecycle. The state machine introduced here drives the agent's procedure, not the application's status. Those are different objects, and conflating them is what produced the prose blob in F8.
