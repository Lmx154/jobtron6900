02

Decisions, already made

These are fixed so no phase reopens them. Two of them change what the workflow engine means by "done" (D3, D4); they are recorded here as architecture, with the invariant each one keeps.

D1
Tags are a text column, not a table.

applications.tags TEXT NOT NULL DEFAULT '', stored as a sorted, lowercase, comma-joined set. Filter with ',' || tags || ',' LIKE '%,x,%'.

Single-user SQLite. A join table buys nothing you can feel and costs a migration, a service, and three tests.

D2
"Attention" is computed, never stored.

Last activity is max(events.starts_at_utc where kind ≠ lifecycle, applied_at, created_at). Staleness thresholds live in one constants block, not in rows.

Stored timestamps drift the moment a write path forgets them. Derived values cannot.

D3
The server auto-applies bank answers that were already approved and fully match.

Inside progress(), before emitting answer_required_question: if the top bank hit is approved and every token of the question matched (coverage == 1.0), apply it as an approved answer with source_label = "question_bank:auto" and move on. Anything less goes to the agent as today.

You approved it once. Approving it again is not a safety check; it is a tax. The invariant that matters — the agent never invents a fact — is untouched because the text came from you. Invariant kept: no unapproved content is ever auto-approved.

D4
One review stop, not one per draft.

prepare_resume and prepare_cover_letter now gate on any version existing, not an approved one. A new step, review_drafts, sits before confirm_submission and stops once with the full list of unapproved items and the frontend URL. New tool applications.approve_drafts.

The step contract is preserved: working steps narrate, stopping steps ask, and the test that asserts a step cannot do both still passes. Status stays user-owned; nothing auto-advances.

D5
Emails are classified by the agent, recorded by one server call.

applications.log_update writes event + status + tags + optional contact atomically. The agent reads the email, proposes one sentence, and calls it on "yes". Same split as start_from_url: the LLM interprets, the server persists.

No email ingestion, no parsing heuristics in Python. You said you're fine handling email; the system just has to make the record cost one word.

D6
Events get a kind: manual, lifecycle, reminder.

Migration 5 backfills lifecycle where dedupe_key ≠ ''. upcoming() hides lifecycle only. A follow-up reminder is kind = reminder with a dedupe key, so it is idempotent and visible.

Today "automatic" and "hidden" are the same bit. A reminder needs to be automatic and shown.

D7
Page capture uses the agent's browser, never the server's.

New tool questions.detect_from_text runs the existing detect_questions on text the agent obtained — from its own browser tool if it has one, from a paste if not. Playwright stays out of Jobtron.

Keeps the rebuild's exclusion intact while removing the reason it hurt.

D8
Inferred flags never overwrite what you set.

cover_letter_required_source ∈ {'', 'inferred', 'user'}. Inference runs only while the source is empty.

A guess that can be silently wrong must be visibly a guess.

Phase 2

The attention rail and follow-up reminders

migration 5independent of P1~1–2 sessions

"What needs me today?" gets a real answer, in the browser and from the agent, from data that already exists.

Schema · migration 5

ALTER TABLE events
  ADD COLUMN kind TEXT NOT NULL DEFAULT 'manual';
UPDATE events SET kind = 'lifecycle'
  WHERE dedupe_key <> '';

EventService.add (core.py:533–559) gains kind="manual"; the lifecycle writer at core.py:727–733 passes kind="lifecycle". upcoming() (core.py:523) changes its predicate from dedupe_key = '' to kind <> 'lifecycle'.

Reminder on Applied

Where applied_at is stamped (core.py:722), also write one event: event_type="Follow-up", kind="reminder", all-day, starts_at_utc = applied_at + FOLLOW_UP_DAYS (7), dedupe_key = f"follow_up:{id}:1". Idempotent by key; visible in Upcoming by kind. A reminder is resolved when any manual event on the same application is dated after it, or the status changed after it.

Service · ApplicationService.attention(now) -> dict

Four buckets, each a list of {application_id, company_name, formal_title, status, days, last_activity_at, tags, reason}. Thresholds are module constants: STALE_DAYS = 14, IDLE_DRAFT_DAYS = 7, HORIZON_DAYS = 7.

BucketRuleReads as
upcomingkind ≠ lifecycle, starts_at_utc within the next HORIZON_DAYS"Interview with Boeing, Thursday"
follow_up_dueunresolved reminder with starts_at_utc ≤ now"Applied 9 days ago, no reply — follow up"
stalestatus ∈ {Applied, Assessment, Interviewing}, last activity older than STALE_DAYS"Interviewing, quiet for 21 days"
idle_draftsstatus ∈ {Draft, Ready to Apply}, created older than IDLE_DRAFT_DAYS, no manual event"Drafted 12 days ago, never sent"

Terminal statuses (Rejected, Withdrawn, Closed) never appear. Sorted within a bucket by days descending.

Surfaces

  • Web dashboard dashboard.py:64–78 — add attention to the context; render a "Today" rail above Upcoming (dashboard.html:25). Each row links to the detail page and carries the same status dot the grid uses (palette.py:10–20). Empty state is one line: "Nothing is waiting on you."
  • MCP — new tool applications.attention. Instruction block gains one shortcut: "What should I do today?" → applications.attention, then ui.show_dashboard.
  • MCP UI ui.py:400 — the applications view opens with the Today list when it is non-empty.
  • Detail page — a single line under the title: "Last activity 9 days ago · next: Follow-up on Sep 16."

Tests · tests/test_attention.py

  • Migration 5 on a v4 database: existing dedupe-keyed rows become lifecycle, others manual; upcoming() output unchanged before/after.
  • Marking Applied creates exactly one reminder; marking Applied again creates none.
  • A manual event dated after the reminder resolves it; one dated before does not.
  • Each bucket with a fixed now: one row that qualifies, one a day short of the threshold, one terminal-status row that must not appear.
  • attention() on an empty database returns four empty lists, not an error.

Accept when

  • The Today rail shows the follow-up reminder seven days after a real Applied, and it disappears after you log the recruiter's reply.
  • "What should I do today?" produces the same list in the chat as on the page.
  • No lifecycle noise returns to the Upcoming rail (regression guard from the rebuild).
Phase 3

Log an update in one sentence

needs P1 + P2~1 session

You paste the recruiter's email. The agent says: "Log Recruiter Contact on Boeing for today, move to Interviewing, tag phone-screen?" You say yes. That is the whole interaction.

Tool · applications.log_update

log_update(
  application_id: int,
  event_type: str,          # free text, UI list suggested
  occurred_at: str,         # display-local or ISO
  notes: str = "",
  status: str | None = None,
  add_tags: list[str] = [],
  contact: {name, role, email, phone} | None = None,
) -> {application, event, status_changed: bool}

One transaction: events.add(kind="manual"), then set_status if given (which still writes its own lifecycle event and the Applied guard at server.py:280–286 still applies — log_update may not set Applied), then tag(add=…), then contact upsert (applications.py:131–133 pattern). Any failure rolls back all four.

Agent contract

Instruction block gains a fourth shortcut, in the same register as the other three:

A pasted email or status update about a job
-> applications.list(query=<company>)
-> propose ONE sentence naming event, date,
   status change (if any), tags (if any)
-> on "yes" call applications.log_update once.
If more than one application matches, ask
which; never guess.

The tool description restates: never set Applied here; never invent a date — use today if the email has none and say so.

Tests · tests/test_log_update.py

  • Full call writes one manual event, one lifecycle event, tags merged, contact created — verified in one read.
  • status="Applied" is refused with the same message as set_status.
  • A contact with an existing email on the same application updates rather than duplicates.
  • A failing status (unknown value) leaves no event behind.

Accept when

  • A pasted rejection email becomes a Rejected status + event + rejected tag after one "yes".
  • The follow-up reminder from P2 resolves as a side effect.
Phase 4

Fewer approvals

workflow semantics · D3, D4needs P0~1–2 sessions

The single largest cut to per-application effort. Two changes to progress(), one new step, one new tool.

A · Auto-apply approved bank answers · core.py:902–913

Before emitting answer_required_question for a question, the server runs search_bank(question.text, limit=1). search_bank (core.py:413–432) adds coverage = matched_tokens / query_tokens to each hit. If the hit is approved and coverage == 1.0, call apply_bank_answer(question_id, entry_id, approved=True, source_label="question_bank:auto"), increment usage_count, and re-evaluate. The loop is bounded by the number of required questions. Only questions that survive reach the agent, whose step text is unchanged.

The application detail page marks auto-applied answers with their source label so you can see — and override — what was reused.

B · One review stop · core.py:915–935 · workflow.py:72–93

Gate changes in the decision chain:

prepare_resumeno approved application_resumeno application_resume version at all
prepare_cover_letterrequired and no approved cover_letterrequired and no cover_letter version at all
review_drafts new—any latest answer version or latest document version is unapproved
confirm_submissioneverything approved, not appliedunchanged

STEP_MAP gains "review_drafts": ("review_drafts", None, "Say say_to_user word for word, including the URL, then stop. When the user approves, call applications.approve_drafts with the ids they named, or all=true.", None). next_action for it carries pending: [{kind: "answer"|"document", id, label}] and frontend_url. The question text lists the pending items in one sentence.

New tool applications.approve_drafts(application_id, answer_ids=[], document_ids=[], all=False) — calls the existing documents.approve (core.py:182–193) and the answer-approval path per id. The percent_complete checks (core.py:789–838) are unchanged: "resume approved" is still a required check; it is simply satisfied later, in one go.

Tests · extend tests/test_workflow_engine.py

  • An approved bank entry with full coverage is applied without the agent ever seeing answer_question; the answer row carries source_label = "question_bank:auto".
  • An unapproved entry, or coverage 0.8, still yields answer_question.
  • From "all questions answered, no documents": steps are generate_resume → generate_cover_letter (if required) → review_drafts → stops. No intermediate stop.
  • review_drafts is a stopping step: waits_for_user is true and say_template is None (the existing "cannot both narrate and ask" assertion covers it once it is in STEP_MAP).
  • approve_drafts(all=True) advances directly to confirm_submission.
  • Total-coverage test of STEP_MAP still passes with the new code.

Accept when

  • A second application to a company using the same six standard questions stops exactly once before "did you submit?".
  • No answer or document is ever marked approved unless it came from an approved bank entry or from approve_drafts.
  • Rebuild finding F8 stays closed: the agent's choice set is still one tool per step.
Phase 5

Page capture through the agent's own browser

needs P0 evidence~1 session

The rebuild fetched server-side and degraded honestly to "please paste". That is still right for the server. But the agent that calls Jobtron usually has a browser tool of its own; let it do the reading.

Tool · questions.detect_from_text

detect_from_text(
  application_id: int,
  page_text: str,
  source: "browser" | "paste",
) -> {detected_questions, count,
      stored_job_description: bool}

Runs detect_questions (posting.py:112–130) on the text; if job_description is empty, stores the text as the description; sets questions_extraction_status = "ok" and questions_extraction_note = source (core.py:756–762). Text is capped at the same 2 MB the fetcher uses.

questions.extract_from_posting gains retry: bool = False, which clears the recorded status before fetching.

Workflow · new step capture_page_text

Emitted when questions_extraction_status ∈ {blocked, empty, error} and questions_reviewed is false — before inventory_questions (core.py:877–895). then_call = "questions.detect_from_text".

you_must:
"If you have a browser tool, open next_action.url,
 read the page's visible text, and call
 questions.detect_from_text with source='browser'.
 If you have no browser tool, say say_to_user word
 for word and stop; when the user pastes the page,
 call questions.detect_from_text with source='paste'."

This is the one step whose wait depends on the client, not the server. It is a deliberate, documented exception to the "server decides whether to stop" rule; waits_for_user is reported false and the fallback is in the instruction. inventory_questions remains the terminal fallback if detection finds nothing.

Tests · extend tests/test_posting.py, test_workflow_engine.py

  • detect_from_text on a saved Workday page fixture finds the same questions the fetcher would on static HTML.
  • After a blocked fetch the next step is capture_page_text, not inventory_questions.
  • retry=True clears status and refetches; retry=False on a recorded status returns the recorded result without a network call.
  • Empty page text does not overwrite a non-empty job description.

Accept when

  • The Workday posting from P0's evidence run completes question extraction without a paste, in a client with a browser tool.
  • The same posting in a client without one still lands on a paste prompt, once.
Phase 6

Inferred flags

migration 6independent~½ session

Small, but it removes a question the agent asks on every application.

Cover letter

ALTER TABLE applications
  ADD COLUMN cover_letter_required_source
  TEXT NOT NULL DEFAULT '';

On every write of job_description, if cover_letter_required_source == '': run infer_cover_letter_required(text) from posting.py — true when "cover letter" appears within 80 characters of required, must, include, attach, submit, or upload; false when it appears only near optional. Set the flag and source = 'inferred'. applications.set_requirements (server.py:250–251) sets source = 'user' and wins forever after.

progress() exposes the source in the cover-letter check's label ("Cover letter (required — inferred from posting)") so the agent can say it and you can correct it.

  • A user-set value survives a later description update that would infer differently.
  • Migration 6 leaves existing rows with source = '', so a re-saved description infers once.

Accept when

Phase 7

Standard answers, asked once

needs P4~1 session

Most ATS forms ask the same dozen things. Answer them once during setup; P4 then applies them silently on every application.

Seed · app/services/standard_questions.py

A literal list of canonical entries, each with a canonical_question and a deliberate keywords set tuned for the token matcher (core.py:413–432). Initial twelve: work authorization · sponsorship now or future · salary expectation · earliest start date · willing to relocate · remote/hybrid/onsite preference · how did you hear about us · previously applied or employed here · security clearance · veteran / disability / EEO voluntary disclosure · LinkedIn / portfolio URL · years of experience in role.

question_bank.seed_defaults() inserts any missing canonical entries with an empty answer and approved = 0. Because search_bank returns approved entries only, unanswered seeds never surface during an application.

Setup surface

  • candidate.readiness (core.py:57–107) gains a non-blocking item: standard_answers: {answered: n, total: 12}. capability is unchanged by it.
  • ui.show_setup and the /profile page render the twelve as a short form; saving an answer marks the entry approved = 1.
  • Instruction shortcut: "What am I missing?" already routes to readiness; it now mentions unanswered standard questions after profile and resume.

Tests · tests/test_standard_questions.py

  • Seeding twice inserts twelve once.
  • For each canonical entry, three real-world phrasings (collected from P0's evidence run and public ATS forms) reach coverage == 1.0 against it, and one unrelated question does not match any seed.
  • An unanswered seed never appears in search_bank results.

Accept when

  • With all twelve answered, a Greenhouse application whose questions are all standard reaches generate_resume with zero answer_question steps.

12

Not doing

  • Email ingestion. No IMAP, no Gmail API, no parsing. You classify; Jobtron records. P3 is the whole of the email story.
  • Playwright in the server. The rebuild's exclusion stands. P5 uses whatever browser the client already has.
  • Auto-submitting. Still permanent. The Applied guard is not touched by any phase; log_update explicitly cannot set it.
  • Auto-advancing status. Reminders and attention buckets are derived views. Nothing changes a status except you.
  • Fuzzy or embedding search in the question bank. P7's keywords plus the existing token matcher are enough for the standard set; anything non-standard still goes to the agent, which is an LLM and can judge.
  • Per-application "considered academic documents" step. Flagged during survey, then dropped: the agent does that work, not you. It costs turns, not effort.
